New guarantees covered by regression tests
------------------------------------------
1. A scan job is bound to the same random browser device token.
2. A completed result is durably stored and replayable for the configured 24-hour free review window.
3. Re-entering the same URL after completion returns the saved result with `fresh_scan_run=false` and consumes no second free usage row.
4. Re-entering the same URL while processing returns the existing job ID and creates no second quota reservation.
5. The legacy synchronous `/api/scan` route remains present.

Important operational boundary
------------------------------
The job record/result is durable in SQLite, but an in-flight scan cannot survive a full application-process restart. If a worker is restarted mid-scan, the stale job is failed after the existing reservation TTL and the failed reservation is recoverable rather than remaining permanently stuck. A distributed queue/worker would be the next step only if Trilloka later runs multiple API instances or requires restart-proof execution.
